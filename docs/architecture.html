ReLife: how the whole system works

ReLife is a personal, local-first life tracker. It pulls in data from your bank, exchange, shopping apps, GitHub, laptop and phone, turns it into one picture of your health, mind, skills, wealth, hobbies and people, and uses games (XP, quests) and an AI of your choice to nudge you toward better days. This page explains every part, how the parts talk to each other, and why it was built this way.

Local-firstRuns on your Mac. Data stays in a Postgres database on your machine.
Two processesA Next.js web app and a long-running worker, sharing one database.
Plug-in shapedA new data source, message format, alert or job is one file plus one line.
Safe to re-runEvery sync and parse dedupes on stable ids, so nothing is counted twice.

1. What ReLife is

Life is split into six areas: Health, Mind, Skills, Wealth, Hobbies and People. Each area page shares one template: a header, a strip of key numbers, then cards. Around them sit:

  • Today (/): the quest log. What to do now: routines due, quests from The System, quick logging.
  • Progress (/profile): level, streak, week, consistency, achievements and XP.
  • Activity (/activity): laptop time from the browser extension and the Mac app watcher.
  • Habits, Insights (alerts, reviews, AI suggestions) and Inbox (messages that couldn't be understood).
  • Connectors (where you connect data sources) and Settings.

You also reach it through Telegram (reminders, one-tap logging, nudges, /ask) and a Chrome extension that shows today's laptop time.

6. Data model

Every table has id, user_id and timestamps. Odd fields go in a meta JSON column and are promoted to real columns only when queried. Money is stored in its original currency and converted at read time (core/fx.convert). Per-day values use the user's local date, never the UTC date, so streaks don't break at midnight UTC.

8. Job engine

Anything that runs on a schedule or on an event is a job. The list is JOBS in src/jobs/index.ts; the engine is src/core/jobs.ts. Job state lives in the Postgres jobs table, so the engine survives restarts and the web and worker never run the same job twice.

Key ideas

  • Lease: a run starts with one conditional UPDATE … WHERE locked_until IS NULL OR locked_until < now(). Only one process wins. The lease lasts timeoutMinutes (default 15, syncs 60).
  • Orphans: leases held by dead processes on this machine (a killed tsx, a reload) are freed on the next tick by checking the PID.
  • Schedules: { everyMinutes } runs at once the first time (so a new connector syncs immediately); { cron } follows your time zone and catches up a missed run once, if within catchUpMinutes.
  • Events: emit('raw.added') sets requested_at on every listening job and wakes the worker with Postgres NOTIFY. A 15-second tick is the fallback.
  • Backoff: after failures, wait failures × interval, at most 6 hours.
  • Gating: enabled() keeps a job idle until its connection exists: a connector must be connected with its keys, Telegram jobs need Telegram, AI jobs need a model.
  • Concurrency: at most 4 jobs at once, each in the background, so a long first sync never blocks reminders.
  • Requests while running are kept, so the job runs once more with whatever arrived meanwhile.

9. Connectors

A connector fetches data from one source and emits raw events with stable ids. It stores its progress in a cursor (ctx.setCursor), so the next sync only fetches what's new. Nothing syncs until you connect it on /connectors. Keys typed there are encrypted; .env only fills blanks.

Shopping apps

These apps have no public API. You log in once in a visible Chrome window; the profile is kept in data/browser/<id> and later syncs reuse the session in a hidden window. Each app has its own history walker (Zomato's web routes, Swiggy's order chaining, Amazon's order cards with year filters). This is personal-use only and never shipped publicly. One Chrome per profile: overlapping syncs wait for each other.

Binance in depth

Binance is the hardest source because its APIs are per symbol and limited in time range:

  • First sync scans every spot pair once with id paging, then only pairs you hold or traded.
  • P2P from 2020 in 30-day windows; Convert from 2021; deposits and withdrawals in 89-day windows, valued at that day's price.
  • Futures income through yearly async downloads (zip files read with inflateRawSync), then API windows.
  • Positions with mark price, liquidation price and margin type; the account's margin ratio is stored in the balance's meta.
  • Older history: the API only goes back about 1.5–2 years. scripts/binance-import.ts imports Binance's Transaction History statements for trades before that.

Parsers turn raw events into records. They run in a fixed order (src/parsers/index.ts); the first one whose match() returns true parses the event. The LLM fallback is always last.

Testing is by sample: each parser has fixtures in src/parsers/fixtures/ as { event, expected }, and npm test runs every fixture. Fixtures use fake account numbers.

Order matching: an app order (Swiggy, Zomato…) is matched to the bank debit it explains, so the spend is counted once, with items. A guard stops two orders claiming the same debit.

11. Wealth and P&L

Wealth has four pages: overview (net worth), Spending, Portfolio and Subscriptions.

Spending

Transactions are categorized by merchant rules (learned from your corrections) and by order items. Food apps count as "Eating out". Items in impulse categories, or bought on many days (a soft drink, a snack), become habit signals for quests and nudges.

Portfolio: profit and loss

loadPortfolio (src/core/portfolio.ts) builds the whole crypto picture in about 25 ms. Profit and loss counts only spot and futures:

How profit and loss is built. Stablecoins count as cash. Money in and out (deposits, P2P) is shown separately, not as P&L.

  • Check: futures reconcile exactly: transfers in and out plus income equals the futures wallet.
  • Known gap: sales of coins bought before the API's history have unknown cost. They count at break-even (no warning is shown).
  • Overview: /wealth reads everything in one call (src/core/wealth-overview.ts): the month's pace against a usual month (one-off big orders counted once), 12 months by category, apps, repeat buys, investments, subscriptions, all-time totals and the latest money nudges.
  • Display: positions under $1 are hidden as dust; coin logos come from CoinGecko, cached in data/coins and served by /api/coins/[symbol].
  • Liquidation: risk is the distance from the mark price to the liquidation price, not the loss on the position's own margin. With leverage on cross margin, a position down 54% on its margin can still be far from liquidation, because the whole wallet backs it.

16. Web app and UI

  • Next.js 16 with Cache Components. Each page renders a static shell at once; DB reads happen in an async child that calls await connection(), inside <Suspense> with a skeleton sized like the content, so nothing shifts. Pages load in 0.07–0.5 s locally.
  • Server actions (src/app/actions.ts) do every write, scoped to getUser(). "Sync now" runs the sync job directly and reports "Already syncing…" if the worker holds the lease.
  • Look: ink black, white and the logo's capsule blue, light-first, with a dark mode. Signature shapes: CapsuleIcon, SystemLabel, the halftone texture in header corners. Routine pictures are Fluent 3D emoji.
  • Charts: one wrapper per kind of number in src/ui/components/charts.tsx (trend, daily bars, ranking, share, sparkline).
  • UI rules: tokens, never raw hex; concentric radius; shadows for depth; buttons press to scale(0.96); named transitions; hit areas of at least 40 px; reduced motion respected; every state change has a static cue. Components are checked in /dev/ui.
  • Mock mode: npm run dev:mock fills relife_mock with random data on port 3001.

18. Reliability

FailureWhat happens
Mac asleep or offiCloud and Gmail hold data; connectors resume from their cursor; cron jobs catch up once; reminders send one catch-up digest instead of a burst.
Connector errorRecorded in sync_runs and the jobs table; backoff up to 6 hours; the connectorFailing rule alerts you.
Worker crash mid-jobThe lease expires, or is freed at once if the process is gone; requests stay queued.
Parser missRegex parsers, then the LLM, then Inbox "Needs review". Retried daily at 03:30.
Duplicate dataImpossible by design: unique keys on raw events and on every derived table.
LLM down or no keyAI jobs skip; rules and rule-based quests keep working.
Worker deadHeartbeat older than 3 minutes shows a banner in the app.
Notification spamDaily caps, quiet hours, once-a-day dedupe per alert, and the watch budget of 2 a day.

Observability is just tables: jobs, sync_runs, llm_runs, raw_events.status, heartbeats. The Connectors page shows "syncing now…", "synced 5 min ago · next in 55 min" or the last error per connector.

19. Performance and scale

  • Load: one person makes roughly 200 raw events a day, about 75,000 a year. Postgres on a laptop handles that with no tuning.
  • Writes: syncs insert raw events in batches of 250; a queue index (user_id, status, at) keeps parsing fast.
  • Reads: pages query directly; the heaviest, the portfolio, takes about 25 ms.
  • No Redis: considered and rejected. Postgres already gives persistence, locking (leases) and wake-ups (LISTEN/NOTIFY). A cache would add a process and stale data without a measurable gain.

Known limits

  • Single user: one global key map, one getUser(). Multi-user needs per-user lookups and row-level security.
  • One global cap of 4 concurrent jobs; browser syncs could get their own limit if Chrome load hurts.
  • Binance history before about 1.5–2 years needs a statement import, and some old sales still have unknown cost.
  • The worker must be running for syncs, reminders and the bot. Moving it and the database to a small always-on machine changes nothing else.
